## 1. Ringkasan Proyek

Webapp **Laravel (PHP + MySQL-ready)** untuk toko/bengkel: mencatat pembelian (stok & histori harga), penjualan manual, dan **Generate Transaksi Otomatis** — merekonstruksi penjualan dari **target omset bulanan** dengan syarat **tidak pernah menjual melebihi stok tersedia pada tanggal tsb**, lalu bisa **export siap import ke POS Bengkel**. Target deploy: shared hosting Hostinger (PHP ≥ 8.2 + MySQL). Lokal memakai SQLite (nol konfigurasi).

## 5. Alur & Aturan Bisnis Penting

### Pembelian
- Form Cash/Hutang (toggle). Cash: bayar ≥ total + PPN (server tolak bila kurang). Hutang: DP + sisa; jatuh tempo auto = akhir bulan ke-3; pelunasan cicilan → lunas saat sisa 0. **Bayar bulk per supplier (FIFO)**: nominal dialokasikan otomatis tertua dulu (`tanggal_transaksi,id ASC`) dalam 1 transaksi atomik; pratinjau wajib sebelum catat; kelebihan = kembalian (tidak dicatat); tiap baris membawa UUID `pembayaran_hutang.grup_bulk` + suffix catatan. Daftar Hutang punya kolom **Sudah Bayar** (= DP + Σ cicilan via `withSum/withCount`, admin & publik) di kanan Sisa Hutang. **Kartu Pembelian** (partial `pembelian/partials/kartu-pembelian`, dipakai dashboard + hutang + lunas, admin & publik): Total Belanja = Σ(total+PPN), sub `N invoice · Sisa`; MENGIKUTI filter halaman masing-masing (dashboard = filter omset; hutang/lunas = periode + supplier tabel, tanpa filter = semua waktu + tanpa suffix supplier); helper `kartuPembelian()` diduplikasi per controller ikut konvensi repo. **Laman Bayar Bulk** (`/pembelian/bayar-bulk`, tab nav ke-4, admin only): form (supplier/nominal/tanggal/**bukti_url opsional** `url|max:1000`/catatan) + riwayat header `bulk_bayar_hutang` (uuid, nominal, dialokasi, kembalian, bukti, jumlah invoice, tombol Batalkan); pratinjau menampilkan link bukti; batal = header + baris hilang; hapus satuan sinkronkan header (hapus header bila tak ada sisa). **Revert pembayaran**: hapus 1 baris (`pembelian.bayar.destroy`) mengembalikan sisa + status; "Batalkan bulk ini" me-revert 1 grup sekaligus (toleran bila sebagian baris sudah dihapus manual). Riwayat pembayaran selama ini write-only — tombol revert ada di detail invoice (admin only, publik tidak ada). **PPN otomatis + override** (`invoice_pembelian.ppn` integer Rp; tarif `toko_settings.ppn_persen` default 11, diubah di Pengaturan): form ada checkbox **PPN otomatis (default centang)** → `PPN = round((Subtotal − Diskon) × tarif/100)` dihitung live via JS & ulang di server (`PembelianService::hitungPpnOtomatis`); hapus centang → input manual dipakai (koreksi e-Faktur, 0 = tanpa PPN). Formula **Sisa Hutang = (Subtotal − Diskon) + PPN − DP**; baris "PPN" tampil di detail & print hanya bila > 0; ikut dihitung saat Edit & di Kembali cash (bayar − (total+PPN)). Edit: status auto awal = centang bila PPN tersimpan == hasil auto DPP saat ini. **Alokasi PPN ke HPP**: item & subtotal invoice tetap memakai harga NETO, tapi **histori harga / `harga_beli_terakhir` / margin & harga jual memakai "harga beli efektif" = neto + bagian PPN** — mode auto/manual invoice-level dialokasikan proporsional per nilai baris (`round(ppn×sub_i/subtotal)` lalu dibagi qty); mode override per-SKU (Excel) memakai PPN baris langsung (`neto + round(ppn_baris/qty)`), sehingga HPP & margin otomatis sudah termasuk PPN. **Import excel kolom PPN (opsional, kolom terakhir) = nominal Rp PER BARIS SKU**: total invoice = **Σ PPN baris** dalam 1 REF (baris kosong = 0); bila **semua baris kosong/0 → otomatis** `round(DPP × tarif)`; PPN negatif ditolak; utk CASH dgn BAYAR_DP kosong, bayar pas = total + PPN (auto/sum). Kolom `invoice_pembelian_item.ppn` menyimpan PPN per baris utk audit. **Metadata invoice per grup REF memakai aturan "nilai pertama yang terisi"** (BAYAR_DP, DISKON_TOTAL, JATUH_TEMPO cukup diisi SEKALI di salah satu baris grup — PPN dikecualikan karena per-SKU). **Jebakan PHP**: setelah `$m = &$groups[$ref]['metadata']` di loop bayar-pas, WAJIB `unset($m)` — kalau tidak, assignment `$m = ...` di loop berikutnya menimpa metadata grup LAIN lewat referensi (bug nyata: grup ke-2 HUTANG/TRIJAYA berubah jadi CASH/PRIMA). **Stok yatim (orphan)**: baris `kartu_stok` jenis `masuk_pembelian` dengan `invoice_pembelian_id = NULL` (keterangan tetap "Pembelian {no_invoice}") TIDAK ikut ter-reverse saat invoice dihapus (`batalEfekPembelian` mencari by invoice id) → stok tertinggal di /barang; muncul bila invoice dihapus di luar alur `PembelianService::hapus` & FK MySQL `nullOnDelete` (SET NULL) men-null-kan kolom tsb. Script `cek-anomali-stok.php` section 4/5/6 mengidentifikasi & mengestimasi stok bersih. **Koreksi**: `scripts/bersihkan-stok-yatim.php` (dry-run default; `--apply` utk eksekusi) — baris yatim di-set qty=0 (tetap ada utk audit, keterangan "(stok yatim dibersihkan)") lalu `barang.stock = SUM(kartu tersisa)` per SKU terdampak.
- Simpan = tambah stok (kartu_stok masuk) + histori harga (harga_jual dikalkulasi ulang hanya saat mode otomatis).
- Edit/hapus atomik dgn guard: hapus invoice hutang ber-historipembayaran **diblokir**; edit dgn qty baru < qty terjual sejak invoice **ditolak**; hapus yang membuat stok minus → warning 2 opsi (force) — **valid di kedua jalur**: non-JS (modal partial resolve-stok-warning) & AJAX (confirm "Lanjutkan/Batalkan" → kirim ulang force=1, lihat app.js). Pesan sukses force menyebut stok minus utk investigasi. **Cek warning hapus dihitung PER SKU (agregat total qty semua baris barang yang sama), bukan per baris** — cek per-baris bisa lolos diam-diam & reversal (yag mengurangi total) membuat stok minus besar tanpa warning (contoh: SKU ganda 4×6=24, stok 10 → hapus → −14).
- **Audit stok**: `scripts/cek-anomali-stok.php` (read-only, jalan `php scripts/cek-anomali-stok.php`) mencetak: (1) barang stok<0 + invoice terkait + 10 kartu terakhir, (2) invoice SKU-ganda + **stok saat ini SKU tsb** (aman/tidak utk dihapus), (3) **drift semua barang** (`barang.stock` vs `SUM(kartu_stok.qty)`) — utk investigasi stok minus & konsistensi data. **Koreksi drift satu-kali**: `scripts/koreksi-kartu-drift-2026-09.php` (dry-run default, `--apply` eksekusi; guard abort bila drift ≠ ekspektasi) — menambah baris kartu `keluar_penjualan` TANPA ubah kolom stock (kolom = fisik, kartu kelebihan krn keluar tanpa nota); dipakai utk 2 SKU Sep 2026 (BL-20570R15-CHA-ECO −13, PCR-18570R14-CHA-ECO −14). Guard hapus invoice memakai kolom `stock`, jadi drift kolom-salah memicu warning palsu — pastikan kolom = fisik dulu sebelum percaya warning.
- **Filter list:** Hutang (`invoice-hutang`) & Lunas (`invoice-lunas`) memiliki filter periode (bulan/tahun/rentang `bulan/tahun/from/to`, prioritas bulan > tahun > rentang) + filter supplier dropdown, berlaku di admin **dan** di `/publik/pembelian/*` (read-only, tanpa bulk/bayar/edit).

### Generate Transaksi (inti fitur)
- Input: periode + target omset; **sisa target = target − transaksi tersimpan di periode** (manual + rekonstruksi).
- Timeline ketersediaan per hari (konservatif: barang masuk hari H baru bisa dijual H+1; **stok awal sebelum periode dihitung sebagai `initialBalance`**); **kapasitas = peak availability × harga** (peak = max stok di awal hari, `final` untuk diagnosa) — `Log::debug` mencatat `kapasitasPeak/Final`, `totalWeight`, `dayTargets`.
- Kapasitas < sisa target → **warning 2 opsi** (lanjut semaksimal / batal) + info **masuk hari terakhir** (nilai stok masuk tepat di tgl selesai — tak terjualable H+1; ada di flash warning, chip review, `parameter_json.masuk_terakhir`, dan log `Generate diagnose`). Target > kapasitas = mustahil matematis; keterisian di bawah kapasitas biasanya stok masuk akhir periode — solusinya perpanjang akhir periode / turunkan target / `variasi_max` > 0, bukan bug.
- Distribusi harian **per-hari proporsional bobot stok tersedia (`avail`), bukan stok masuk**, dengan jitter ±20%; **qty acak 1..`maks_qty`** (bukan `floor(sisa/price)` deterministik) + unit-pool fill (SN qty=1 + NO_SN unik; non-SN NO_SN kosong; variasi harga −10%..0%, tidak pernah < harga beli; jam operasional & hari libur dipatuhi); **global fill** untuk sisa target & `penyesuaianAkhir` agresif (batch top-up, iterasi 300) — **keduanya SELALU jalan** (target sudah di-capped `min(sisa,kapasitas)` di `generate()`; dulu di-skip saat kapasitas kurang sehingga mode "semaksimal stok" tidak maksimal). **Fix penting:** `hariBatas` habis tidak lagi `unitSisa=-1` global (hanya `soldToday` per hari), sehingga tidak ada hari lompat.
- **Basis harga generate = `barang.harga_jual` (MASTER)** — harga jual efektif dari histori_harga TIDAK dipakai utk basis generate (tombol "Terapkan Margin" di Pengaturan yang meng-update master langsung memengaruhi draft generate; kapasitas & peek juga master); variasi & floor ≥ harga beli (`harga_beli_terakhir`, termasuk alokasi PPN) tetap. Histori tetap utk audit/export modul lain.
- **`maks_qty_item_per_nota`** (default 3) membatasi unit 1 SKU dalam 1 nota (mis. 4 = 1 nota bisa 1-4 ban); **`maks_sku_per_nota`** (default 1) membatasi **jumlah jenis barang berbeda per nota** — default 1 = tiap nota hanya berisi 1 SKU (barang non-SN yang sama digabung jadi 1 baris dgn qty ≤ cap; SKU SN tetap 1 baris qty=1 + NO_SN unik), disarankan utk toko ban (1 nota = 1-4 ban dari 1 SKU). `penyesuaianAkhir` menambah qty item juga dibatasi cap yg sama. Parameter diatur di Pengaturan → Parameter Generate (dan bisa di-override per generate).
- Ref nota unik global (`refBebas` — baris "dibatalkan" tetap menempati ref).
- Sinkron per request (< 5 detik; ramah shared hosting). Draft tersimpan di DB → review/edit → **Simpan** (potong stok, tandai SN, label rekonstruksi).
- **Undo batch tersimpan**: reversal stok+SN → status `dibatalkan` (baris dipertahankan utk audit); ditolak bila ada nota diedit.
- **Riwayat** (`/generate/riwayat`) urut terbaru di atas (`latest('id')`); batch **draft & dibatalkan** bisa **dihapus** (AJAX, route generate.hapus-batch) — cascade items+transaksi+batch; batch **tersimpan ditolak** (hapus nota via halaman Penjualan, undo via tombol Undo).

### Tracking Stok (/stok-tracking — Stock Aging Report)
- Tujuan: lihat stok yang masih tersisa dari batch pembelian per bulan, utk prioritas menghabiskan stok terlama (FIFO) via penjualan manual.
- **Algoritma**: per barang dgn stock > 0, ambil semua kartu_stok masuk (masuk_pembelian, stok_awal, opname positif) + keluar (keluar_penjualan); simulasi FIFO — tiap keluar menghabiskan batch paling tua; sisa per batch = qty asli − yg dikonsumsi. Batch dgn sisa > 0 ditampilkan.
- View: **Ringkasan Total Stok Keseluruhan** (luar filter — query `Barang::sum('stock')`) + **filter bulan** (checkbox; default semua bulan) + tabel per bulan (SKU, kode, sumber Pembelian/Stok Awal/Penyesuaian, tgl masuk, qty awal, sisa, umur hari).
- Catatan: opname bisa positif/negatif; pemfilteran & tampilan tabel berbasis bulan dari batch tersisa.

### Rekap Stok per Merk (/rekap-stok — cermin dokumen stok Word)
- Tujuan: keterlihatan stok ban — susunan **Merk → Varian → baris (UKURAN | KODE | NAMA | STOK)**, tiap merk ber-header total SKU + total stok, grup `Tanpa Merk` selalu paling bawah.

## 6. Jebakan Teknis yang Diketahui

- **PhpSpreadsheet v5**: validasi memakai `PhpOffice\PhpSpreadsheet\Cell\DataValidation` (+ `setSqref` lalu `setDataValidation`); `setShowDropDown(false)` = panah tampil (konvensi terbalik); `setColumnWidth` tidak ada → pakai `getColumnDimension()->setWidth()`.
- **Reader vs Writer PhpSpreadsheet (jebakan shared hosting)**: `Reader\Xlsx` (dipakai import pembelian/barang/update-harga via `bacaSheet()`) butuh ekstensi **simplexml, dom, xml, xmlreader**; `Writer` (download template & export A/B) **cukup xmlwriter + zip**. Gejala khas di Hostinger: export & download jalan, tapi upload Excel 500/putih karena web PHP-FPM belum mengaktifkan ekstensi XML-reader (CLI SSH bisa beda dgn FPM). Mitigasi: `ExcelImportService::cekEkstensiExcel()` = pre-flight (dipanggil di tiap template/import, lempar `ImportFileException` dgn pesan jelas) + ketiga controller import meng-catch `Throwable` → `Log::error` + flash ramah (tidak pernah 500 putih lagi); kartu "Status Lingkungan Excel" di Pengaturan utk diagnosa cepat. Validasi upload: `mimes:xlsx, max:10240`.
- Cache statis `HargaService::$cacheHarga` bocor antar-test → reset di setUp. **`GenerateService::hargaBarang` memakai cache INSTANCE `$hargaCacheBarang` + reset di awal `generate()`** (JANGAN `static` — id barang bertabrakan antar-test/proses).
- **GenerateService jebakan yang sudah diperbaiki:** `hariBatas = timeline - simSold - soldToday`; habis per hari hanya `soldToday=PHP_INT_MAX`, **jangan** `unitSisa=-1` global (bug hari lompat); `initialBalance` = sum `kartu_stok.qty` sebelum periode wajib dihitung (stok Mei untuk generate Juni); bobot harian = `avail` (stok tersedia di awal hari), bukan `masuk` hari itu; `nota_min/max` kini 1–100 (validasi & view `max=100`) untuk target 1.2B; `penyesuaianAkhir` iterasi 300 + batch top-up.
- Instance model bisa **stale** setelah reversal stok → `->fresh()` sebelum mutasi.
- String PHP dgn backslash utk formula Excel (mis. "$A$1") mudah error escaping; tulis hati-hati.
- **Selector kelas dgn slash** (mis. `.bg-red-50/70`) di CSS tulis-tangan: slash WAJIB diescape (`.\bg-red-50\/70`) atau dihindari — Lightning CSS (Vite) memperingatkan & browser bisa membuang aturan. Kalau utilitas dipakai lewat `@apply` (mis. `bg-red-50/70` di `.row-overdue`), override dark mode targetkan **kelas hasil mount** (`.dark .tbl tbody tr.row-overdue`), bukan nama utilitas.
- Timezone app `Asia/Jakarta`; `date` shell bisa beda dgn `now()` Laravel saat scripting.
- **Rate limiter WAJIB di provider, bukan routes file**: `RateLimiter::for()` di `routes/web.php` tidak dieksekusi per-request saat `route:cache` aktif → POST /login 500 "Rate limiter [login] is not defined" (hanya di hosting, lokal aman). Limiter `login` ada di `AppServiceProvider::boot()` + test regresi `AuthTest::test_rate_limiter_login_terdaftar_di_provider`.
- Tambah status baru → pastikan semua query laporan tetap filter `tersimpan`.
- **DILARANG DDL dalam transaksi (MySQL implicit commit!)**: `ALTER/CREATE/DROP/TRUNCATE` di dalam `DB::transaction` membuat MySQL commit paksa diam-diam → transaksi hilang → "There is no active transaction" + atomisitas jebol (insiden restore backup 08/09/2026 di hosting: data sudah masuk semua tapi tampil 500). SQLite lokal tidak terpengaruh sehingga lolos test. Aturan: transaksi hanya DML (`delete()`, bukan `truncate()`); sequence/auto-increment diperbaiki SESUDAH commit; FK toggle di luar transaksi.
- **Urutan FK migration (MySQL vs SQLite)**: FK yang menunjuk ke tabel yang dibuat oleh migration dgn timestamp *belakangan* GAGAL di MySQL/MariaDB (error 1005 "Foreign key constraint is incorrectly formed") tapi lolos diam-diam di SQLite dev (FK tak di-enforce). Contoh historis: histori_harga, referensi_sn, kartu_stok menunjuk ke invoice_pembelian & transaksi_penjualan. **Aturan**: definisikan kolom FK *tanpa constraint* di migration asli (cukup foreignId(...)->nullable()), lalu tambahkan constraint-nya di *migration terpisah* setelah kedua tabel ada (lihat 2026_09_06_000001..000004: Schema::table(...) + $table->foreign(...) + ->nullOnDelete()). SQLite mendukung Schema::table()->foreign()/dropForeign via strategi rebuild tabel, jadi migrate:fresh lokal tetap hijau — tapi wajib diverifikasi di MySQL sebelum deploy.
- **FK `kartu_stok` (2026_10_02_000001)**: `invoice_pembelian_id` & `transaksi_penjualan_id` diubah dari `nullOnDelete` → **`restrictOnDelete`** — invoice/penjualan yang masih punya baris kartu_stok TIDAK bisa dihapus di luar alur aplikasi (mencegah stok yatim); alur hapus aplikasi selalu `batalEfekPembelian/batalEfekPenjualan` dulu (hapus baris kartu), jadi tetap aman.
- **Overflow horizontal mobile = flexbox `min-width:auto` (insiden 2026-09-24)**: `body{display:flex}` + `main{flex-1}` mempunyai `min-width:auto`, sehingga `main` **menolak menyusut** di bawah lebar *min-content* isinya (`input[type=file]` intrinsik ~300px, tabel, strip kartu) → seluruh dokumen lebih lebar dari viewport (scroll horizontal) dan elemen rata-kanan terdorong keluar layar (gejala khas: nilai kolom `tbl-cards` tampak "kosong"/terpotong). **Fix**: `main` diberi kelas `min-w-0` (`layouts/app.blade.php`) + guard global di `app.css` `body{overflow-x:hidden}` & `main{min-width:0}`. Anaknya yang flex juga butuh `min-w-0` (mis. pembungkus `overflow-x-auto` & file input). Jangan dihapus.
- **Bottom nav `#bottom-nav`**: `position:fixed !important; bottom/left/right:0; z-index:40` + `md:hidden` + `padding-bottom: env(safe-area-inset-bottom)`, isi 5 item (Dashboard/Barang/Stok/Beli/Jual) dgn `route(($publik?'publik.':'').…)` & `aria-current`. Konten utama diberi `pb-24 md:pb-…` agar tak tertutup; footer disembunyikan di mobile (`hidden md:block`); toast mobile naik `bottom:72px !important`. **Pernah "ikut scroll"** (diagnosa: halaman Beli/Jual) — karena itu `!important` & `z-40` (di atas konten & `seg-bar` z-20) wajib dipertahankan; disembunyikan di `@media print`.
- **Toggle lipat = `<x-collapse>` (checkbox + `peer`), JANGAN `<details>` duplikat**: elemen toolbar berisi **`id` unik** (`bulk-print-btn-{scope}`, `bulk-delete-count-{scope}`) — kalau markup diduplikasi utk mobile+desktop, `getElementById` di `app.js`/`partials/bulk-print` menabrak & tombol desktop mati. `x-collapse` = **satu instance DOM**: `<input type=checkbox class="peer sr-only">` + `<label md:hidden>` + `<div hidden peer-checked:block md:block>` — desktop (≥768px) selalu terbuka via `md:block`, mobile tertutup kecuali diceklis, **tanpa JS & tanpa FOUC** (specificity `peer-checked:block` (0,2,0) mengalahkan `.hidden` (0,1,0)). Pasangan `partials/filter-periode` utk form filter (mobile `grid-cols-2`, desktop `md:flex wrap`). Pindahkan ke `x-collapse` bila menemui `<details>` ganda (dashboard lama sudah dimigrasi).
- **Controller Publik vs Admin dgn nama class sama WAJIB alias**: `use App\Http\Controllers\X;` di dalam `namespace App\Http\Controllers\Publik;` + deklarasi `class X` di file yg sama = fatal *"Cannot redeclare class"* (insiden `Publik\RekapStokController`). Pola benar: `use App\Http\Controllers\X as AdminX;` (lihat route yg sudah pakai alias `... as PublikXController`).
